Raspberry Pi を触るたびに毎回うろ覚えになりがちな、SSH まわりのセキュリティ設定についての自分用メモです。

今回あらためて整理したのは、次の3つです。

1. **SSHポートをデフォルトの22番から変更する**
2. **パスワード認証をやめて鍵認証にする**
3. **Fail2ban を導入する**

この3つは、全部まとめて「SSH を固くする設定」として覚えがちですが、実際には役割が少しずつ違います。どの層で攻撃を止めるのか、どこまで処理を通してしまうのか、という観点で見ると理解しやすかったので、その整理を残しておきます。

特に Raspberry Pi のような低消費電力・低スペック寄りの環境では、侵入を防げるかどうかだけでなく、**不要な通信処理をどれだけ手前で落とせるか** も重要そうです。この記事では、この3つの対策を OSI 参照モデルと負荷軽減の観点で備忘録としてまとめます。

なお、ここでいう OSI レイヤーの話は、Linux や OpenSSH の実装を厳密にそのまま 7 層へ割り当てるというより、どの段階で処理が止まるかを理解するための整理として使っています。

---

## 1. まずは役割をざっくり整理

| 対策内容 | 対象となるレイヤー層 | 主なセキュリティ効果 |
| :--- | :--- | :--- |
| **ポート変更 (22222 など)** | **第4層（トランスポート層）** | 自動 Bot の無差別スキャンに引っかかりにくくする |
| **Fail2ban (UFW/iptables 連携)** | **主に第3層〜第4層付近** | 攻撃元 IP を早い段階で遮断し、上位層へ通しにくくする |
| **鍵認証** | **第7層（アプリケーション層）** | 正しい秘密鍵を持たないログイン試行を拒否する |

自分なりの理解では、この3つは同じ仕事をしているわけではありません。

ポート変更は「見つかりにくくする」対策、Fail2ban は「しつこい相手を途中で締め出す」対策、鍵認証は「最後の認証を突破させない」対策、と考えると整理しやすいです。つまり、**低いレイヤーから順に負荷ごと削っていく多層防御**として見ると分かりやすい、というのが今回の学びでした。

ただし Fail2ban 自体は最初からパケットを直接見ているわけではなく、いったん認証失敗のログを見てから遮断ルールを入れる仕組みです。なので、最初の数回の試行までは sshd 側に届く、という理解のほうが正確です。

---

## 2. どこで止めるかで負荷が変わる

今回いちばん腑に落ちたのは、通信を拒否できるかどうかよりも、**どの層まで処理を進めたうえで拒否するのか**で負荷が変わる、という点です。

同じ「拒否」でも、カーネルが早い段階で捨てるのか、sshd が起きて暗号処理や認証処理まで進んでから失敗させるのかで、CPU とログ書き込みの負荷はだいぶ変わりそうです。

```text
[OSI参照モデル]
第7層: アプリケーション層  ── SSH daemon (sshd) ★ログ書き込み & 鍵検証 (最も重い)
第6層: プレゼンテーション層 ── (暗号化処理: SSHハンドシェイク)
第5層: セッション層         ── (SSHセッション確立)
第4層: トランスポート層     ── TCP (ポート22222)
第3層: ネットワーク層       ── IP / ufw (Netfilter/iptables) ★ここで遮断 (最も軽い)
第2層: データリンク層       ── Ethernet (NIC)
第1層: 物理層               ── 物理ケーブル / Wi-Fi
```

## 3. 攻撃を受けたときの動きの違い

### Fail2ban なしの場合

鍵認証にしていて、ポートも 22 番から変えていたとしても、相手にそのポートを見つけられればアクセス自体は届きます。その場合、処理は sshd が動くところまで進みます。

- 第3層〜第4層: IP パケットと TCP の接続要求を受け取り、SSH サービスへ渡す
- 第6層: SSH のハンドシェイクに伴う暗号処理が走る
- 第7層: sshd が認証を行い、失敗内容をログへ書き出す

侵入そのものは防げても、試行回数が多ければ CPU 使用率は上がりますし、ログも増えます。SD カード運用の Raspberry Pi では、この継続的な書き込みも気にしておいたほうがよさそうです。

### Fail2ban ありの場合

Fail2ban はログを見て一定回数以上失敗した IP を検出し、その IP を UFW や iptables に流して遮断します。つまり、最初の数回は通常どおり sshd まで到達しますが、BAN 後の通信はかなり手前で落とせます。

- 第3層〜第4層付近: Netfilter/iptables が BAN 済み IP からの通信を遮断する
- 第4層以降: sshd まで処理が届かない
- 結果として、暗号処理もログ出力も発生しにくくなる

この差は、低スペックな環境ほど効きそうです。アプリケーション層まで毎回相手をしてから拒否するより、ネットワーク層で落とせるほうが軽い、というのは素直に納得できました。

## 4. Raspberry Pi でこの3つをセットにする意味

Raspberry Pi では、CPU 性能もストレージ性能も余裕があるとは言えません。だからこそ、SSH の防御を「認証の強さ」だけで考えるより、「そもそも余計な処理を増やさない」という見方も大事だと感じました。

- ポート変更で、雑なスキャンに見つかる回数を減らす
- Fail2ban で、繰り返し来る相手を早い段階で遮断する
- 鍵認証で、認証突破そのものを防ぐ

この3段構えにすると、役割がきれいに分かれます。ポート変更はノイズを減らし、Fail2ban は負荷を抑え、鍵認証は最後の防壁、という整理で覚えておくと忘れにくそうです。

## 5. まとめ

SSH のセキュリティ対策は、単に「どれが一番強いか」で見るより、**どのレイヤーで、どれだけ早く不要な通信を止められるか**で見ると整理しやすい、というのが今回の結論です。

Raspberry Pi のような環境では特に、鍵認証だけでなく、ポート変更と Fail2ban を組み合わせて上位層に仕事をさせない構成にしておくと、セキュリティ面だけでなく運用面でも意味がある、と理解しました。
